# SEES Nexus — Backend

FastAPI backend for the SEES Nexus v2 rebuild. This package covers the pieces
owned by the backend lead: repo/CI scaffold, local dev environment, the Auth
vertical, and the Admin vertical. Full architecture, schema, and API contract
live in the Technical Documentation v2 — this README only covers running this
codebase.

Place this folder at `backend/` in the project's monorepo, alongside `frontend/`.

## Quick start (Docker — recommended)

```bash
cp .env.example .env
docker compose up --build
```

This brings up Postgres, runs Alembic migrations, seeds sample data, and
starts the API on `http://localhost:8000`. Interactive docs: `/docs`.

Seeded accounts (dev only — rotate before any shared/staging use):
- `admin@seesnexus.dev` / `ChangeMe123` (ADMIN)
- `student@seesnexus.dev` / `ChangeMe123` (STUDENT)

## Quick start (without Docker)

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
# Uncomment the SQLite DATABASE_URL line in .env — no Postgres needed this way.
python seed.py            # optional
uvicorn app.main:app --reload
```

## Running tests

```bash
pytest app/tests -v
```

Tests run against an isolated in-memory SQLite database per test — no
external services required. Every endpoint has a happy-path test and at
least one auth/permission-failure test, per the Tech Doc's non-functional
requirements.

## Database migrations

Schema changes go through Alembic — never edit tables by hand in a shared
environment.

```bash
alembic revision --autogenerate -m "describe the change"
alembic upgrade head
```

Review autogenerated migrations before committing; autogenerate doesn't
always catch everything (e.g. some enum or index changes).

## What's implemented here

- **Auth vertical**: `/api/v1/auth/{register,login,refresh,validate/token,me}`,
  `/api/v1/notify/{send-code,verify-code}` (OTP-gated registration)
- **Admin vertical**: `/api/v1/admin/{dashboard,users,users/{id}/role,users/{id}
  (deactivate),loans,loans/{id}/approve,loans/{id}/reject}`
- **Projects vertical**: `/api/v1/projects` — public paginated list (filterable
  by `category` and `status`) and public detail; create is open to any
  authenticated user, while update and delete require the creator or an admin.
  `member_ids` replaces the member set wholesale; `thumbnail_url` stores a
  Cloudinary URL supplied by the client, since this backend never uploads.
- Standard `{status, message, data}` response envelope, including for errors
- JWT access/refresh tokens with type checking
- `Hardware`/`HardwareLoan` models (needed for the admin loans endpoints);
  `Event`/`Article` are minimal stand-in tables so the dashboard
  counts real rows instead of hardcoded numbers — replace/extend them when
  those verticals are built for real, keeping the table names the same.

## Not implemented here (other verticals / later milestones)

Hardware CRUD (beyond loans), Events, Articles, and the `/upload`
Cloudinary integration are out of scope for this slice — see the task
assignment sheets for who owns each.
